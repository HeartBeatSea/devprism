## 1. 背景与目标

### 1.1 为什么做这个项目

目标岗位 JD 的职责第 2 条写得很具体：

> 参与**工具调用、技能开发、工作流配置、知识库处理**等基础功能实现

职责第 1 条点明了两个业务场景：**经营分析、研发效能**。

所以项目的目标不是"做一个 Agent"，而是**用这四项基础能力，解决一个真实场景的问题**，并且做到可演示、可验证。

### 1.2 为什么选"研发效能"而不是"经营分析"

| 维度 | 研发效能 | 经营分析 |
|---|---|---|
| 数据可得性 | Git / GitHub，真实、免费、零造假 | 需要造一套业务库，假数据说服力弱 |
| 结论可验证 | 提交记录、PR 时间戳可逐条核对 | 假数据的结论无法证伪 |
| 演示效果 | **可以让面试官拿自己的仓库现场跑** | 只能跑自己的假数据 |
| 与岗位相关度 | JD 明确点名 | JD 明确点名 |

**结论：选研发效能。** 唯一性优势是"现场演示真实数据"。

### 1.3 项目目标（按优先级）

1. **求职**：产出可演示、可讲解、有量化指标的作品，覆盖 JD 职责第 2 条全部四项
2. **学习**：亲手实现 Agent 的四个基础模块，而不是调用现成框架
3. **可复用**：架构上留出扩展点，后续可接"经营分析"场景

## 2. 用户与场景

### 2.1 用户画像

| 用户 | 诉求 | 关键约束 |
|---|---|---|
| **研发 Leader**（真实使用者） | 快速知道团队这周健康不健康、风险在哪 | 没时间看图，要结论；结论要能追溯到数据 |
| **面试官**（演示对象） | 5 分钟内判断候选人能力 | 只有一次机会，必须现场跑通 |

### 2.2 核心场景（用户故事）

- **US-1**：作为研发 Leader，我想问"我们团队最近三个月的交付效率怎么样"，得到一份带数据的结论，而不是一堆图表。
- **US-2**：作为研发 Leader，我想知道"哪些模块只有一个人在维护"，提前识别关键人依赖风险。
- **US-3**：作为研发 Leader，我想知道"我们的提交规范执行得怎么样"，并看到不符合规范的具体例子。
- **US-4**：作为面试官，我想输入一个仓库地址，30 秒内看到一份像样的报告。

### 2.3 反场景（明确不服务）

- ❌ 用于给个人打绩效分、排名
- ❌ 用于实时监控大屏
- ❌ 用于替代 Jira / 项目管理工具

## 3. 竞品与现状调研

### 3.1 市面上已有的东西

| 类别 | 代表产品 | 能力边界 |
|---|---|---|
| 一体化研发管理 | ONES、Jira、Azure DevOps | 度量与工作流同源，但需要团队整体迁移 |
| 工程效能分析 | Pluralsight Flow（原 GitPrime）、LinearB、Jellyfish | 深挖 Git/CI 数据，做指标可视化 |
| 云厂商套件 | 阿里云云效效能洞察 | 与云生态绑定，90+ 指标卡 |
| 开源自建 | Apache DevLake | 多源数据入湖，内置 DORA 等指标 |

参考：[2026 年研发效能度量工具选型指南](https://ones.cn/blog/tools-curated/2026-rd-efficiency-measurement-tools-guide-3)、[Apache DevLake](https://github.com/apache/incubator-devlake)

### 3.2 它们共同的天花板

以上所有产品的形态都是 **仪表盘（Dashboard）+ 固定指标**：

1. **人要先知道该看什么**——你得自己选指标、选时间范围、选维度
2. **只回答"是什么"，不回答"为什么"**——看到评审延迟上升，工具不会告诉你原因
3. **不会主动给建议**——数据摆在那，解读靠人
4. **需要预先建模**——新指标要开发、要配置

### 3.3 我们的差异化定位

> **不做又一个仪表盘，做仪表盘之上的"解释层"。**

| 能力 | 现有工具 | 本项目 |
|---|---|---|
| 获取数据 | ✅ | ✅（复用同样的数据源） |
| 计算指标 | ✅ | ✅（实现一组核心指标） |
| 自然语言提问 | ❌ | ✅ |
| 自主选择分析路径 | ❌ | ✅（Agent 自己决定查什么） |
| 解释原因、给建议 | ❌ | ✅ |
| 结论可追溯 | 部分 | ✅（强制引用工具调用结果） |

**一句话定位**：把"看报表"变成"问问题"，把"数据"变成"结论"。

## 4. 功能需求

优先级定义：**P0 = 没有它项目不成立；P1 = 体现 JD 四模块完整性；P2 = 加分项**。

### P0 — 最小可用闭环

| ID | 需求 | 说明 |
|---|---|---|
| FR-1.1 | 本地 Git 仓库接入 | 解析 `git log`，无需网络、无限流，**作为主数据源** |
| FR-1.2 | GitHub 公开仓库接入 | REST API，支持配置 Token；作为补充数据源 |
| FR-1.3 | 增量同步 | 按时间戳增量拉取，结果缓存到本地库 |
| FR-2.1 | 提交维度指标 | 提交频次、时段分布、Conventional Commits 合规率 |
| FR-2.2 | 变更维度指标 | 增删行数、文件变更热度、超大文件（>800 行）识别 |
| FR-2.3 | 协作维度指标 | PR 数量、首次评审延迟、合并周期、WIP（未合并 PR 数） |
| FR-2.4 | 风险维度指标 | 文件级巴士因子、单人依赖模块、长期未动的高频变更文件 |
| FR-3.1 | 工具注册中心 | 每个工具声明 name / description / JSON Schema |
| FR-3.2 | 参数校验与结构化错误 | 校验失败返回可被 LLM 理解的错误信息，供其自我纠正 |
| FR-3.3 | 内置工具 ≥ 8 个 | 覆盖数据查询、指标计算、知识检索、报告输出 |
| FR-4.1 | ReAct 推理循环 | Thought → Action → Observation，限制最大轮数（默认 8） |
| FR-4.2 | 工具调用失败自纠 | 错误回灌给模型，最多重试 2 次 |
| FR-4.3 | 结论强制引用 | 报告中的每个数字必须标注来源工具与参数 |
| FR-4.4 | 拒答机制 | 数据不足以支撑结论时明确说"无法判断"，禁止编造 |
| FR-5.1 | Markdown 报告 | 结构：概览 → 关键指标表 → 风险项 → 建议 |
| FR-5.2 | 报告导出 | 输出 `.md` 文件，可归档、可对比 |

## 6. 数据需求

### 6.1 数据源优先级

**本地 Git 仓库优先，GitHub API 作为补充。** 理由：

- 本地 git 无网络依赖、无限流、隐私可控
- GitHub REST API 未认证约 60 次/小时，带 Token 约 5000 次/小时（**以官方文档为准**）——直接拿它做主力会被限流卡死

### 6.2 数据量假设

| 项 | 假设值 |
|---|---|
| 仓库历史 | 1–3 年 |
| Commits | 500–5000 |
| 贡献者 | 1–50 |
| PR | 50–1000 |

### 6.3 可计算指标清单

**流动效率**：提交频次、PR 合并周期、吞吐量（周均合并 PR 数）、WIP

**质量与稳定**：Revert 提交占比（变更失败率的近似）、超大文件数、单文件变更频次

**协作健康**：首次评审延迟、评审参与人数、提交时段分布（是否长期深夜赶工）

**结构风险**：文件级巴士因子、单人维护模块、高变更 × 低测试覆盖的文件

> ⚠️ **指标口径必须在文档中写死**。Cycle Time / Lead Time 各家用定义不同，不写清楚会被面试官追问穿帮。

## 7. 约束与假设

- **人力**：1 人开发
- **周期**：3 周核心 + 1 周打磨
- **不做**：用户系统、多租户、权限体系、高可用
- **不做**：模型训练与微调
- **不自己写**：静态代码分析（复杂度、重复率）——用现成库（radon / lizard），自研没有收益

---

## 8. 明确不做（Out of Scope）

这一节和功能需求同等重要，**能说清"不做什么"反而体现工程判断力**。

- ❌ **个人绩效考核与排名**——研发效能领域最大的坑。指标一旦用于考核就会被"游戏化"（Goodhart's Law），所有成熟产品都明确规避。**面试时主动说这一点，是专业信号。**
- ❌ 实时监控大屏
- ❌ 代码托管 / CI/CD 平台
- ❌ 自动修改代码 / 自动提 PR
- ❌ 多租户 SaaS 化

---

## 9. 验收标准（Definition of Done）

1. 输入任意公开 GitHub 仓库 URL 或本地仓库路径，**90 秒内**产出一份 Markdown 报告
2. 报告中 **≥ 80% 的结论**能追溯到具体工具调用结果
3. 评测集（≥30 条）上**工具选择准确率 ≥ 85%**
4. 新机器 clone 后 `docker compose up` 成功，README 步骤可完整复现
5. 有一段 **3 分钟演示视频**，展示"输入仓库 → 出报告"全过程

## 10. 风险清单

| ID | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | GitHub API 限流 | 演示失败 | 本地 git 兜底；结果缓存；降低调用频次 |
| R2 | LLM 输出不稳定，报告质量波动 | 演示翻车 | 结构化输出 + Schema 校验 + 模板兜底 |
| R3 | 指标口径被质疑 | 面试减分 | 文档写死定义，主动说明局限 |
| R4 | 时间不够 | 交付不完整 | 砍 P1：只保留 FR-6 知识库一项，放弃 Skill 与工作流 |
| R5 | 分析真实仓库涉及隐私 | 合规问题 | 只用公开仓库或本人仓库；本地 git 不上传 |
