# 研发效能周报 — pallets/click

## 一、结论先行

1. **提交活跃度健康，但节奏偏"夜猫子 + 周三集中"**：180 天窗口内共 307 次提交，周均 11.9 次，夜间提交占比 38.1%，周三为峰值日（70 次）。[来源: 提交数据]
2. **协作侧是本周最大瓶颈：评审供给严重不足**。435 个 PR 创建、仅 122 个合并（合并率 4.7/周），平均评审次数仅 0.93 次，24.6% 的合并未经评审，P90 周期高达 281.2 小时。[来源: 协作数据]
3. **周期中位数尚可（22.3h），但长尾极重**：中位数与 P90 相差约 12.6 倍，说明少数 PR 长期滞留，拉高了整体交付周期。[来源: 协作数据]
4. **提交规范无法从现有数据判定**：本次数据未提供"规范提交占比"字段，只能以参照规范提示风险阈值（<50% 时变更日志难以自动生成），不对该仓库下合规结论。[来源: git-convention.md#Git 提交信息规范 / 与效能指标的关系]

### 2.3 规范参照（仅作参照，不作合规判定）

- 分支保护参照：`main` 要求至少 1 条 approve、CI 通过、分支最新，绕过需在周会说明。[来源: branch-strategy.md#分支与发布策略 / 分支保护]
- 评审时效参照：PR 提交后 24 小时内应给出首次反馈；超 48 小时未响应视为评审阻塞，应转派。[来源: review-checklist.md#Code Review 检查清单 / 评审时机]
- 提交规范参照：规范提交占比 <50% 时变更日志无法自动生成、回溯成本上升，建议用提交钩子校验。[来源: git-convention.md#Git 提交信息规范 / 与效能指标的关系]

> 说明：以上为参照标准。本仓库 24.6% 的未评审合并、0.93 的平均评审次数与"至少 1 条 approve"的参照存在张力，但数据未区分是否走了保护豁免流程，故仅提示关注，不下"不合规"结论。

## 三、可执行的改进建议

1. **给评审加"24h 首响"看板与自动转派**：以 22.3h 中位数为基线，把超过 24h 无首次反馈的 PR 自动标记并转派给备选评审人，目标把 P90 从 281.2h 压到 100h 以内。参照 [来源: review-checklist.md#Code Review 检查清单 / 评审时机]。
2. **针对 24.6% 未评审合并做抽样复盘**：区分"紧急热修走豁免"与"评审缺失"两类，前者要求在周会记录原因（参照 [来源: branch-strategy.md#分支与发布策略 / 分支保护]），后者纳入评审覆盖率周指标，目标先降到 15% 以下。
3. **在提交钩子中校验提交信息格式，并输出"规范提交占比"指标**：当前周报缺该字段，建议补采；以 50% 为预警线（参照 [来源: git-convention.md#Git 提交信息规范 / 与效能指标的关系]），同时结合凌晨 4–6 点的高产时段，评估是否将 CI/评审提醒错峰推送，减少夜间提交的评审等待。
