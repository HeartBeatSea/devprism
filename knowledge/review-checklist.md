# Code Review 检查清单

## 评审时机

PR 提交后 24 小时内应给出第一次反馈。超过 48 小时未响应，视为评审阻塞，应主动转派给其他评审人。

## 必查项

- 是否有对应的 issue 或需求编号
- 变更是否只做了一件事，有没有夹带无关改动
- 新增逻辑是否有测试覆盖
- 错误处理路径是否完整，异常是否被吞掉
- 日志是否包含足够的上下文，有没有打印敏感信息
- 数据库变更是否可回滚
- 是否有硬编码的配置、密钥、地址

## 评审意见的写法

区分「必须修改」和「建议」。必须修改的用 `must:` 前缀，建议用 `nit:` 前缀，避免作者猜测你的意图。

反例：`这里不太好吧` —— 没有说明哪里不好、要改成什么。

正例：`must: 这个循环在空列表时会抛 IndexError，建议先判空`

## 合并条件

- 至少一条 approve
- CI 全部通过
- 无未解决的 must 级评论
- 分支已与主干同步

## 无评审合并的风险

已合并 PR 中没有任何评审记录的比例，是衡量评审是否形同虚设的直接指标。该比例超过 50% 时，代码质量完全依赖作者个人，缺乏制衡。
